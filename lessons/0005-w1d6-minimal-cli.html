把结构化输出装进一个可用的 CLI

今天把 W1D5 的模型调用、解析、校验和重试组织成一个可交互的需求澄清助手。重点不是堆功能，而是划清交互层、业务流程和模型适配层的边界。

今日可验证成果

  • 能拒绝空需求并清理用户输入
  • 能把原始需求、问题答案和修改意见合并为下一轮输入
  • 能区分模型草稿和用户确认后的最终结果
  • 交互层不直接承担解析、校验和重试细节
  • 至少 5 个 CLI 纯函数测试通过
  • 完成日志、配置和错误处理的最小设计

0. W1D5 闭卷热身（10 分钟）

先在 notes/W1D6.md 回答两题：

  1. json.loads、Requirement.model_validate 和 request_requirement 分别负责什么？
  2. 为什么没有 open_questions 也不能直接视为最终结果？

1. 先看完整链路（15 分钟）

用户输入
  → 输入校验
  → Prompt
  → 模型调用
  → JSON 提取与解析
  → Pydantic 校验
  → 展示草稿和待确认问题
  → 收集答案与修改意见
  → 再次分析
  → 用户确认
  → 输出最终任务

CLI 的职责是组织这条流程和与用户交互。W1D5 的 request_requirement() 已经负责结构化输出和有界重试，W1D6 不应复制这部分逻辑。

2. CLI 不是一段大函数（15 分钟）

把程序分为四类职责：

职责负责内容
输入层读取命令行参数和用户输入，拒绝空需求
领域流程决定分析、提问、修改、确认的顺序
模型适配调用 W1D5 的结构化输出流程
展示层把任务、验收标准、错误和下一步提示显示给用户

这样做的直接收益是：纯函数可以脱离终端测试，模型可以被假的 call_model 替换，交互流程也不会和 SDK 细节纠缠在一起。

3. 先实现两个纯函数（25 分钟）

打开 labs/w1d6/cli.py，实现：

validate_requirement(text: str) → str
build_final_requirement(original, answers, revision="") → str

契约如下：

  • 需求先执行 strip()，全为空白时抛出 ValueError
  • 问题答案为空或只有空白时，不写入下一轮输入
  • 答案顺序与传入字典的顺序一致，方便用户核对
  • 修改意见非空时单独标记为“用户修改意见”
  • 没有修改意见时，不生成空的修改意见段落

4. 状态机先于交互循环（20 分钟）

模型生成的是草稿，用户确认的是最终结果。即使 open_questions 为空，也必须经过确认状态，因为用户可能需要修改模型的任务拆分、措辞或范围。

COLLECT_REQUIREMENT
  → ANALYZE_DRAFT
  → CONFIRM_DRAFT
  → COLLECT_ANSWERS（有问题时）
  → ANALYZE_FINAL
  → CONFIRM_FINAL
  → DONE

用户拒绝草稿时，不能悄悄继续使用旧结果；应该收集修改意见或重新输入需求，再进入下一轮分析。

5. 配置、日志与错误（20 分钟）

模型名、重试上限等运行配置应从参数或环境变量进入，密钥不得写入源码。用户输出应保持简洁，开发日志则记录调用阶段、尝试次数和异常详情。

用户可见：需求不能为空，请重新输入。
开发日志：结构化输出失败，attempt=2，error=JSON 解析失败。

错误处理要区分三类：

  • 输入错误：在调用模型前处理，不消耗模型请求
  • 模型调用错误：记录日志，并根据策略重试或终止
  • 输出格式或结构错误：交给 W1D5 的 repair prompt 和有界重试处理

6. 测试与验收（25 分钟）

先运行当前脚手架，确认测试会因为两个函数尚未实现而失败：

uv run pytest labs/w1d6/test_w1d6.py -q

实现后至少覆盖以下场景：

  • 普通需求首尾空白被清理
  • 空字符串、空格、换行和制表符被拒绝
  • 非空答案进入最终需求
  • 空答案被过滤
  • 修改意见存在时被单独加入
  • 修改意见为空时不出现空段落
  • 多个答案保持原有顺序
